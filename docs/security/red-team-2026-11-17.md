## Findings

### RTA-01 — Arbitrary OAuth `origin` accepted into callback URL (medium defense-in-depth concern; exploitation unproven)

- `core/routes/authentication/providerRedirect.ts` accepted `origin: z.string()`.
- `core/routes/authentication/addMasterPin.ts` accepted the same input.
- `core/routes/authentication/oauthMethods.ts` concatenated the supplied origin and `/{purpose}/callback` before using it in the authorization flow.
- The upstream OAuth provider may reject unregistered redirect URIs, so a token leak or auth bypass is **not** established.
- Remediation in this PR: accept only exact HTTP(S) origins with a host matching the incoming request Host; reject paths, queries, userinfo and foreign hosts. The Host header is not an authoritative trusted allowlist; deployment must enforce allowed Host values at reverse proxy too.
- Verify against both direct HTTP and TLS-terminating reverse proxy deployments.

### RTA-02 — Unhandled HTTP errors reflect exception message (low–medium information disclosure, confirmed source behavior)

- `core/modules/WebServer/middlewares/topLevelMw.ts` built a 500 response containing `error.message`.
- Different failing routes may produce system paths or sensitive implementation details; no such payload was actively triggered.
- Remediation: generic client-facing error while preserving server-side logging.

### RTA-03 — Untrusted forwarded proto can set cookie Secure attribute (low configuration integrity, confirmed source behavior)

- `core/modules/WebServer/middlewares/sessionMws.ts` accepted `X-Forwarded-Proto` without verifying the direct TCP peer.
- This does not demonstrate session theft or an HTTPS downgrade. It can break session behavior for certain plain-HTTP clients.
- Remediation: require a trusted direct proxy configured in `TXHOST_PROXY_IP_RANGES` before consulting the header.
- Deployment note: configure proxy IP ranges and preserve original Host and forwarded-proto headers as intended.

### RTA-04 — Throttled requests ended without an HTTP response (medium availability concern; confirmed source behavior)

- `core/modules/WebServer/index.ts` returned immediately if HTTP load or per-IP limiter refused a request.
- Without `res.end()` these requests depend on connection cleanup and can retain resources longer than needed.
- Remediation: respond `429` / `503`, close response promptly and publish `Retry-After`.
- Validate under bounded load in isolated staging; do not stress live services.

## Privileged attack impact / review observations

- `core/routes/advanced/runCommand.ts` checks `all_permissions` before dispatching commands. `core/routes/advanced/groups/processCmds.ts` intentionally allows reading `process.env` and writing heap snapshots. Treat `all_permissions` as equivalent to system/secret access, and avoid granting it to ordinary moderators.
- `core/modules/WebServer/middlewares/authMws.ts` requires a CSRF token for web API requests and a separate token for NUI/intercom; these are positive controls, not confirmed bypasses.
- `core/modules/WebServer/webSocket.ts` rechecks auth and permission for subscribed command events and applies room permission changes during admin refresh. Review event-room coverage and races under test before claiming a bypass.
- `core/modules/FxScreenStreams.ts` uses viewer tokens, checks ownership, rate/size limits, and periodically revokes sessions when permission or credentials change. No anonymous stream access confirmed from static review.

## Candidate red-team chains (unproven; test on isolated instance)

1. Anonymous request → login/OAuth endpoints → session fixation and CSRF → administrator actions.
2. External client → trusted/untrusted proxy headers → IP classification → NUI/intercom authentication.
3. Limited admin → permission-restricted HTTP and WebSocket commands → privileges after account modification or revocation.
4. Admin viewer → capture session → account disabled/permission revoked → ongoing screen frames.
5. Hostile recipe/config input → path/URL validation → filesystem/command execution boundaries.
6. Flood of malformed but bounded requests → limiter/load-shedding → socket and heap resource management.
